# 新着表示ゲート撤廃 デプロイ手順（本番Pi作業用）

本番環境（Raspberry Pi、`https://x-image-collector.stella-kanon.com`、このリポジトリ直下が
そのまま本番環境）で、Web版の「新着ポストの表示ゲート撤廃」を反映するための手順書。

**この手順書の想定読者はPi上で作業するエージェント/作業者**。上から順に実行し、
各ステップの「確認」を満たしてから次に進むこと。特に**手順2→手順4の順序を入れ替えると
画像一覧が一時的に壊れる**ため、順序厳守。

---

## 背景と変更内容

### これまでの挙動（変更前）

cronの定期取得で保存した画像は `revealed=false` で保存され、一覧クエリ
（`listMedia()`）が `revealed == true` で絞り込んでいたため、**画面上の
「最新を取得」ボタンを押すまで新着が表示されなかった**。

### 変更後の挙動

- `listMedia()` から `revealed` の絞り込みを削除。cronが保存した時点で一覧に出る。
  ログインし直す・リロードするだけで新着が見える。
- `revealed` フィールドは「**新着として通知済みか（既読フラグ）**」の意味に転用。
  表示の可否には一切関与せず、新着バナーの件数表示にだけ使う。
- 新着バナー「✨ 新着ポストがあります（N件）」は**通知として残る**。
  ボタンのラベルは「最新を取得」→「**表示を更新**」に変更。
  役割は「開きっぱなしのタブでグリッドを先頭から読み直す＋既読にしてバナーを消す」。
- Firestoreのフィールド名 `revealed` は**変更していない**（既存ドキュメントの移行と
  Android側 `FirestoreMirror.kt` の変更を避けるため）。データ移行は不要。

### 変更ファイル

| ファイル | 変更内容 |
| --- | --- |
| `frontend/lib/repo/media.ts` | `listMedia()` から `where('revealed','==',true)` を削除（中核の変更） |
| `frontend/app/(app)/page.tsx` | バナーのボタンラベルを「表示を更新」に変更 |
| `firestore.indexes.json` | `revealed` を含まない一覧用インデックスを4件**追加** |
| `frontend/worker/batch.js`, `app/api/reveal/route.ts`, `app/api/collect/route.ts` | コメントのみ（挙動の変更なし） |

**`.env` に追加・変更した項目はない。**

## 手順

### 手順0. 作業前の状態確認

```bash
cd <本番リポジトリのパス>   # このリポジトリ直下が本番環境
git status
git log --oneline -3
docker compose ps
```

**確認**: 作業ツリーがクリーンであること。ローカルに未コミットの変更がある場合は、
**勝手に捨てずに内容を報告して指示を仰ぐこと**（本番環境で直接編集された修正が
残っている可能性がある）。

### 手順1. コードを取得

```bash
git pull origin main
git log --oneline -3
```

**確認**: `feat: 新着ポストを取得時点で一覧に表示し、バナーは通知のみにする` の
コミットが入っていること。

> この時点ではまだ何も反映されない（アプリはコンテナ内のビルド済みバンドルで
> 動いているため）。**手順4でリビルドするまで本番の挙動は変わらない**。

### 手順2. Firestoreインデックスをデプロイ（★アプリのリビルドより先に必ず実行）

新しい一覧クエリは `revealed` を含まないため、`revealed` を含まない複合インデックスが
必要になる。**これが無い状態で新コードを動かすと、画像一覧の取得が
`FAILED_PRECONDITION` で失敗し、画面に「画像一覧の取得に失敗しました」と出る。**

```bash
firebase deploy --only firestore:indexes --project x-image-collector
```

**認証について**: このPiでは firebase CLI に常設のログイン情報を置いていない。
過去（2026-07-06のユーザーツリー統一作業）は**一時的なサービスアカウント鍵**を置いて
`GOOGLE_APPLICATION_CREDENTIALS` 経由で実行し、**作業後に鍵ファイルを削除**した。
同じ方式で実行すること。鍵が用意できない場合は、ここで作業を止めて報告する
（Firebaseコンソールから手動でインデックスを作成する選択肢もあるが、
`firestore.indexes.json` の定義と食い違うため非推奨）。

> **注意**: 既存インデックスの削除を促すプロンプトが出た場合は「**いいえ / 削除しない**」を
> 選ぶこと。今回の変更はインデックスの**追加のみ**で、既存の `revealed` 付き
> インデックスはロールバック余地を残すために意図的に残してある（後片付けは手順7）。

追加されるインデックス（すべて `mediaAssets` コレクション）:

1. `x_user_id` ASC + `posted_at` DESC + `media_key` DESC
2. `x_user_id` ASC + `is_face` ASC + `posted_at` DESC + `media_key` DESC
3. `x_user_id` ASC + `is_favorite` ASC + `posted_at` DESC + `media_key` DESC
4. `x_user_id` ASC + `is_face` ASC + `is_favorite` ASC + `posted_at` DESC + `media_key` DESC

### 手順3. インデックスのビルド完了を待つ（★ここで待たないと壊れる）

インデックスは作成コマンドが返っても**すぐには使えない**。バックフィルのビルドが
完了して `Enabled`（有効）になるまで数分かかる。

```bash
firebase firestore:indexes --project x-image-collector
```

またはFirebaseコンソール → Firestore Database → インデックス で、上記4件がすべて
**「有効 / Enabled」**（「作成中 / Building」ではない）になったことを確認する。

**確認**: 4件すべてが有効になるまで手順4へ進まないこと。

### 手順4. アプリをリビルド・再起動

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f frontend
```

**確認**: ログに `[worker] scheduled: "*/60 * * * *"` が出て、コンテナが
`running` になること。エラーが出ていたらログを添えて報告する。

> ビルドはPi上だと時間がかかる。`NEXT_PUBLIC_*` はビルド時にバンドルへ焼き込まれるため、
> `--build` を省略してはいけない。

### 手順5. 動作確認

ブラウザで `https://x-image-collector.stella-kanon.com` を開き、以下を確認する。

- [ ] ログインでき、画像一覧が表示される
- [ ] **アカウントの絞り込みチップ**を切り替えて一覧が出る（複数選択・単一選択の両方）
- [ ] **「🙂 顔のみ」** で絞り込んで一覧が出る
- [ ] **「🌟 お気に入り」** で絞り込んで一覧が出る
- [ ] **「顔のみ」＋「お気に入り」の同時適用**で一覧が出る
- [ ] 無限スクロールで2ページ目以降が読める
- [ ] 共有リンク（`/s/<token>`）を開いて一覧が出る／顔のみ絞り込みも動く

> **フィルタの組み合わせを一通り触るのが重要**。組み合わせごとに使うインデックスが
> 違うため、インデックス不足はここで初めて表面化する。
> 「画像一覧の取得に失敗しました」が出たら手順3に戻り、対象のインデックスが
> 有効になっているか確認する。

新着バナーの確認（cron待ちが必要なので任意）:

- [ ] 未読の新着がある状態で「✨ 新着ポストがあります（N件）」が出る
- [ ] **バナーが出ている時点で、既にその新着画像が一覧の先頭に並んでいる**（これが今回の変更の本体）
- [ ] 「表示を更新」を押すとバナーが消え、以後リロードしても再表示されない

> **X APIはリクエスト課金**（`UNIT_COST_USD_*` 参照）。動作確認のために
> 「取得を開始」や「過去の投稿をさらに読み込む」を**むやみに押さないこと**。
> cronは60分ごとに回るので、新着バナーの確認は次回のcron実行を待てばよい。
> 急ぐ場合はFirestoreコンソールで `users/{OWNER_UID}/mediaAssets` を
> `revealed == false` で絞って件数を見れば、バナーの表示条件だけは確認できる。

### 手順6. 完了報告

以下を報告する。

- 手順1で取り込んだコミットハッシュ
- 手順2〜3で有効化したインデックス4件の状態
- 手順5のチェック結果（失敗した項目があればスクリーンショット/ログ付きで）

### 手順7. 後片付け（★数日〜1週間、安定稼働を確認してから。急がなくてよい）

`revealed` を含む既存インデックスのうち、以下**3件は今回の変更で未使用**になった。
安定稼働を確認できたら `firestore.indexes.json` から削除してデプロイしてよい。

- `x_user_id` + `revealed` + `is_face` + `posted_at` + `media_key`
- `x_user_id` + `revealed` + `is_favorite` + `posted_at` + `media_key`
- `x_user_id` + `revealed` + `is_face` + `is_favorite` + `posted_at` + `media_key`

**`x_user_id` + `revealed` + `posted_at` + `media_key` は削除しないこと。**
新着件数のカウント（`countUnrevealed()`）が今も使っている。

## ロールバック

**インデックスは追加のみで既存を消していないため、アプリのコードを戻すだけで
完全に元の挙動に戻る。** Firestoreのデータ移行も行っていないので、データ側の
巻き戻しは不要。

```bash
git log --oneline -5                      # 変更前のコミットを特定
git revert <マージコミット> -m 1           # または git checkout <変更前コミット>
docker compose up -d --build
```

追加した4つのインデックスは残しても害はない（ストレージを少し使うだけ）。
気になる場合のみ、ロールバック後にコンソールから削除する。

## 補足: 既知の制限（今回は未修正）

推しアカウントが**31件以上**ある場合、新着件数のカウント（`countUnrevealed()`）は
Firestoreの `in` クエリ上限（30件）で先頭30件しか数えない。そのため31件目以降の
アカウントの新着はバナーの件数に乗らない。

ただし**今回の変更で画像自体は表示されるようになった**ため、実害は
「バッジの件数に乗らない」だけに縮小している。修正は別途。
